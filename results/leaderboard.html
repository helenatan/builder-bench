How it works & methodology

What this measures

The non-engineer “builder” job-to-be-done: a product manager describes what they want and expects a coding agent to build it end to end. Unlike SWE-bench (engineers fixing bugs in mature repos), these tasks turn on vague specs, judgment calls about messy data, and “just make it work.”

Scope of this run

15 tasks · 3 Claude tiers (Opus 4.8 · Sonnet 4.6 · Haiku 4.5) · one neutral harness (the Claude Agent SDK), subscription-billed. v1 is Claude-only on a single harness; cross-model and cross-harness comparisons are future work. Exact model ids: claude-opus-4-8, claude-sonnet-4-6, claude-haiku-4-5-20251001.

How a task works — Task → Run → Report

Every task freezes a Goal (what's asked) and an Answer Key (what counts as correct). A Contestant (the model) runs it in the same neutral harness as everyone else and produces an Output — the deliverable plus the full transcript. The Report layer then scores that output. Open any task to see all of these.

How grading works — two surfaces

Every task has a programmatic grader that checks the deliverable: does it run, is the number right, does the data persist. Where the behavior is the point, an LLM judge also reads the transcript — did the agent clarify a vague ask, did it flag the hidden data trap. The judge is itself a model, so its grades don't count until they match human labels (the bar: Cohen's κ ≥ 0.7); until then the programmatic checks stay primary.

The four categories

A task's difficulty has to live somewhere in its design — a trap in the Setup, a Goal that's hard to pin down or to hold onto, an Output that must actually ship, or an Answer Key that hinges on judgment. Each category is named for which part is hard: the Setup (D Messy World), the Goal (A Vague Ask, B Long Haul), or the Output (C Full Build). Each one's full description sits above its rows in the matrix.

Metrics

Pass@1 — unbiased single-attempt solve probability (Chen et al. 2021 estimator across 3 independent attempts); orders the board, shown with a 95% Wilson CI on the rounded integer count. Pass@3 — probability of solving given exactly 3 draws (same estimator, k=3); where all 3 attempts succeed or fail together, it equals Pass@1. Cost / solved (headline) — total spend across all attempts ÷ tasks solved, so wasted spend on failures and retries is priced in; “—” when nothing solved. Cost / task — total spend ÷ tasks attempted, a pure price that stays defined even at zero solves; the gap between the two is the reliability tax of retries. Effort / task — average tool calls and agent turns, the non-dollar half of the economic profile. Costs are imputed at public list prices (runs are subscription-billed), shown to two significant figures — total ≈$27 this run.

Limitations — read before citing

  • Small n. 3 attempts per task (15 tasks); 95% CIs still overlap across tiers at this sample size, so the ladder is a capability profile, not a firm ranking.
  • Low discrimination. 12 of 15 tasks pass or fail on every tier — the order turns on 3 tasks.
  • Judge not yet validated. The behavioral grades come from an LLM judge whose agreement with human labels has not been measured yet, so any judge-dependent claim is provisional. Programmatic checks remain primary.
  • Category mix. Messy World is 40% of the suite, weighting the aggregate toward judgment-heavy tasks.
  • Not an isolation boundary. Agent tool calls run host-side in a temp local workdir — the sandbox is for reproducibility, not security.
